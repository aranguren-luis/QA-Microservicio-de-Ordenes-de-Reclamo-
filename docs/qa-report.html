1. Resumen Ejecutivo

Se ejecutaron 29 de los 31 casos planificados contra producción (24 automatizados + 5 manuales). De estos, 28 resultaron correctos y 1 falló (TC-013). Los 2 casos manuales restantes requieren entorno controlado y quedan pendientes. El flujo de éxito responde 201 con envelope estándar, la validación del DTO devuelve 422 VALIDATION_ERROR con sus detalles, la idempotencia por Idempotency-Key funciona correctamente y el pipeline de guards e interceptores se comporta como se espera. Se detectaron 5 hallazgos: BUG-001 (body >100KB devuelve 500 en vez de 4xx — en fix), BUG-002 (DTO sin @MaxLength — en fix), BUG-003 (no existe endpoint para listar órdenes — asignado), BUG-004 (licencia SAE viaja en el body — cerrado) y BUG-005 (nationalId aceptaba guiones — fix aplicado, asignado).

2. Objetivo y Alcance

  • Verificar que el endpoint POST /v2/companies/{companyId}/orders cumple el contrato definido en el código auditado del repositorio: envelope { data, error, meta }, status codes y el pipeline real de guards, pipes e interceptores.
  • Contrastar los 30 casos del plan (TC-001..TC-030) contra la implementación (auditoría caso a caso) y contra el comportamiento del entorno desplegado (https://api.qa.mock.com).
  • Diseñar y ejecutar la suite automatizada (22 casos) con la aserción exacta que falló y su motivo.

Fuera de alcance: GET /health y cualquier otro endpoint; UI / navegador (la suite usa solo APIRequestContext); pruebas de carga, rendimiento y seguridad ofensiva.

3. Pipeline del Request (orden real de ejecución)

POST /v2/companies/{companyId}/orders
  └─ 1. ThrottlerGuard               → 429 RATE_LIMITED si >5/min por IP (corre antes de la auth)
  └─ 2. KeycloakIntrospectionGuard   → 401 si Bearer inactivo/ausente
  └─ 3. QuotaGuard                   → 429 QUOTA_EXCEEDED si >100/día (consume cuota incluso con body inválido)
  └─ 4. IdempotencyInterceptor       → 422 si falta Idempotency-Key / 201 cached si la key ya existe
  └─ 5. CompanyValidationPipe        → 404 Not Found si UUID no registrado (comportamiento del despliegue)
  └─ 6. ValidationPipe (DTO)         → 422 VALIDATION_ERROR si body inválido
  └─ 7. CreateOrderService.execute() → encola job en BullMQ
  └─ 8. CreateOrderProcessor (async) → POST hacia SAE (regional)
  └─ 9. ResponseEnvelopeInterceptor + ApiStandardExceptionFilter → todo response en { data, error, meta }

Toda respuesta (éxito o error) va envuelta en { data, error, meta } con traceId = trc-<uuid>.

5. Registro de Hallazgos

BUG-001 — El servidor responde 500 INTERNAL_ERROR ante un body de más de 100 KB (el límite aplica al body total: orderDetails, orderDetailId o ambos) en vez de un 4xx limpio

Campo Detalle
ID BUG-001 (caso TC-013)
Título El servidor responde 500 INTERNAL_ERROR ante un body de más de 100 KB — el límite del parser de Express (102400 bytes) aplica al body total, por lo que el 500 ocurre sin importar si el exceso viene de orderDetails, orderDetailId o ambos — en vez de rechazarlo con un 4xx limpio (413 o 422)
Severidad Sev2 (alta)
Esperado 4xx limpio (413/422) con envelope estándar — el servidor no debe fallar por tamaño de entrada
Actual 500 INTERNAL_ERROR — PayloadTooLargeError del body-parser (límite default Express 100 KB) no mapeado por el filtro
Reproducción POST /v2/companies/{uuid}/orders con body > 102400 bytes — el exceso se probó con ambos campos (orderDetails 60k + orderDetailId 60k ≈ 120 KB); el 500 ocurre igual si el exceso viene solo de orderDetails o solo de orderDetailId
Evidencia — response del servidor {"data":null,"error":{"code":"INTERNAL_ERROR","message":"Unexpected server error","traceId":"trc-<uuid>"},"meta":null}
Estado En fix

BUG-002 — El DTO no valida la longitud de los campos (acepta 5000 caracteres)

Campo Detalle
ID BUG-002 (caso TC-013)
Título El DTO no limita la longitud de orderDetails ni orderDetailId: una petición con ambos campos de 5000 caracteres responde 201 en vez de un rechazo de validación (no tiene @MaxLength)
Severidad Sev3 (baja)
Esperado Rechazo 422 VALIDATION_ERROR cuando un campo supera una longitud máxima razonable (@MaxLength en el DTO)
Actual 201 con el envelope de éxito (status: "queued") — el DTO acepta strings arbitrariamente largos
Reproducción POST /v2/companies/{uuid}/orders con orderDetails y orderDetailId de 5000 caracteres cada uno en la misma petición
Evidencia — response del servidor {"data":{"message":"Order creation process initiated","status":"queued"},"error":null,"meta":null}
Estado En fix

BUG-003 — No existe endpoint para listar o consultar las órdenes

Campo Detalle
ID BUG-003
Título El microservicio solo permite crear órdenes (POST /v2/companies/{companyId}/orders): no existe endpoint para listar los orderDetailId de una empresa ni para consultar el estado de una orden
Severidad Sev2 (media)
Esperado Un endpoint GET /v2/companies/{companyId}/orders (o similar) que liste las órdenes / orderDetailId creadas y/o permita consultar el estado de una orden por orderDetailId o Idempotency-Key
Actual No existe — el catálogo de rutas solo expone POST /v2/companies/{companyId}/orders y GET /health; el resultado del procesamiento (éxito o rechazo de SAE) queda en la caché Redis del worker (idempotency:processor:*) sin ningún endpoint que lo exponga
Reproducción Inspección del catálogo de rutas del código auditado (create-order.controller.ts y health.controller.ts): no hay GET de listado ni consulta por orderDetailId / Idempotency-Key
Evidencia — catálogo de rutas {"endpoints":["POST /v2/companies/{companyId}/orders","GET /health"]}
Estado Asignado

BUG-004 — El dato de Licencia no debería existir en el body de creación de órdenes

Campo Detalle
ID BUG-004
Título El worker inyecta el dato de Licencia (Lic) en el body de creación de la orden (create-order.processor.ts) — la licencia SAE es configuración de la empresa, no un dato de la orden
Severidad Sev3 (baja)
Esperado El body de creación solo debe contener datos de la orden (orderDetailId, orderDetails, contractId, nationalId); la licencia debe resolverse/validarse por la empresa destino, no viajar como dato del body
Actual El worker agrega Lic: license al payload SAE — el dato de licencia viaja en el body de la orden (el cliente no lo envía; viene de companies.sae_license en BD o de SAE_LICENSE_{DO,PE,VE} en env)
Reproducción Inspección del worker: create-order.processor.ts construye el payload SAE con Lic: license (línea 102), resuelto de la BD o el env según la empresa
Evidencia — payload SAE {"id_det_orden":"ORD-1001","detalle_orden":"Mantenimiento de fibra","id_contrato":"CONT-9988","Cedula":"V-12345678","Lic":"<license de la empresa>"}
Estado Cerrado

BUG-005 — El campo nationalId acepta caracteres especiales (guiones) en vez de solo strings numéricos

Campo Detalle
ID BUG-005
Título El campo nationalId acepta caracteres especiales como guiones (ej. V-12345678) en vez de rechazarlos con una validación de solo caracteres numéricos
Severidad Sev3 (baja)
Esperado El campo nationalId solo debe aceptar strings numéricos (sin guiones ni caracteres especiales)
Actual Acepta cualquier string, incluyendo guiones y caracteres especiales (ej. V-12345678)
Reproducción Enviar un body con nationalId: "V-12345678" — responde 201 en vez de rechazar con validación
Evidencia — payload {"nationalId":"V-12345678"}
Estado Asignado
