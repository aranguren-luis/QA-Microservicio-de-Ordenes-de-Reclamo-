Objetivo de la Reunion

Ejecutar y validar manualmente los casos de prueba criticos para el microservicio de Ordenes de Reclamo, con un enfoque central en el comportamiento del Idempotency Key y las colas Bull.

1. Ejecucion Tecnica de la Prueba

1.1 Verificacion de existencia de claves y colas

Se ejecuto el comando KEYS idempotency:* y KEYS bull:orders-queue:*. Se confirmo la presencia de las claves correspondientes a las pruebas.

1.2 Validacion de expiracion y reutilizacion del Idempotency Key

Se valido el flujo de la clave, ejecutando el comando TTL en distintos momentos:

  • Resultado del TTL inicial: 0 (la clave estaba a punto de expirar)
  • Renovacion en tiempo real: El TTL decremento secuencialmente de 22 a 17
  • Eliminacion final: El TTL arrojo -2, demostrando que la clave fue eliminada al expirar

1.3 Validacion del TTL configurado

Se ajusto la variable REDIS_INDEPOTENCIA_TTL a 64 segundos. El TTL arrojo valores decrecientes: 86012, 86009, 86008, 86006, 86005 segundos.

1.4 Validacion de la cola de trabajos completados

Se inspecciono el conjunto ordenado de trabajos finalizados mediante ZRANGE bull:orders-queue:completed 0 -1 WITHSCORES.

1.5 Validacion del payload de idempotencia

Se ejecuto GET idempotency:request:...:QA-PRUEBAS para verificar el contenido persistido.

  • Payload devuelto: "Order creation process initiated","status":"queued"
  • Conclusion: El sistema de idempotencia persiste correctamente el estado como "queued"

2. Temas Tratados y Decisiones del Equipo

2.1 Dificultades con herramientas de monitoreo de Redis

Se probaron varias alternativas y se decidio usar la Redis CLI via terminal (Docker) para consultas en tiempo real.

2.2 Ajuste del TTL en entorno de pruebas

El TTL original era de 86400 segundos (24 horas). Se modifico a 64 segundos para agilizar las pruebas de ciclo de vida.

2.3 Revision de reportes de pruebas automatizadas

Se detectaron falsos negativos en reportes previos. Se decidio actualizar los esquemas de validacion.
